# Resume Rewrite — producing the bullet

The output standard: bullets the candidate would say aloud in an interview,
carrying proof a stranger can believe. This file is why the skill exists —
the difference between a resume that labels the work and one that shows it.

## The bullet standard — concrete first, category second

Lead with the lived thing: what changed · what shipped · what was hard · what
the candidate personally controlled · what became possible after. The
category label, if kept at all, comes **after** the concrete thing — never
instead of it. A line that could belong to 200 other resumes is not done.

## PCOPO lens — Problem / Change / Ownership / Proof / Outcome

Use the lens to find what is MISSING from a bullet; never force all five
parts into one line.

- **Problem** — what was limited, broken, slow, unclear, risky, manual,
  expensive, underperforming.
- **Change** — what moved from before to after because of the candidate.
- **Ownership** — what they personally owned, drove, designed, built,
  reviewed, fixed, delivered.
- **Proof** — system type · scale · users · team size · technical surface
  area · production use · constraints · metrics · before/after comparison.
- **Outcome** — what got better: revenue, cost, speed, reliability, quality,
  risk, adoption, customer value, new capability.

## Voice test — reject the rewrite if

It sounds like a polished LinkedIn bot · category labels stand in for lived
detail · impressive words carry no proof · the candidate would not say it
aloud in an interview · the real work is hidden behind abstraction.

Ban list: results-driven · proven track record · leveraged · spearheaded ·
dynamic · passionate · seasoned professional · transformational ·
cutting-edge · innovative solutions · AI-native · robust scalable solutions ·
*end-to-end* without proof · *scalable* without scale · *production* without
production details.

## Truth rules

- Truth tags: `confirmed` · `inferred` · `needs-confirmation` · `risky` ·
  `cut-unless-proven`. JD-language echo is still `needs-confirmation` until
  the candidate's own history supports it.
- **Metric rule.** Never invent a number; never let an estimate become a
  fact. Suggest metric categories only — revenue · cost · delivery speed ·
  cycle time · defect rate · onboarding time · adoption · users ·
  transactions · uptime · support volume · customer impact · risk reduction ·
  compliance — and ask what the candidate can defend.
- **Interview-risk check.** A claim implying daily coding, deep ML,
  production ownership, architecture depth, security expertise, or people
  leadership that the history weakly supports → reposition, add proof, reduce
  the claim, or prep the defense. Never leave it armed.
- **AI-coded work is hands-on** when the candidate owned design, review,
  correctness, security, integration, and delivery. Clarify the operating
  model plainly — never imply manual coding, never apologize for the
  leverage. Canonical form: *"Used AI to write code while reviewing
  correctness, quality, security, and delivery-readiness."*

## Domain-neutral transformation rules

Do not learn the rewrite by copying a stock before/after sentence. Recover the lived mechanism:

1. Replace the category label with the specific thing changed.
2. Name the before-state and after-state when both are known.
3. Name who used, received, or benefited from the work.
4. State what the candidate personally controlled.
5. Add one constraint or proof point that makes the claim believable.
6. End on the observable consequence; ask for it when missing.

Use only the parts supported by the candidate’s evidence. A missing part becomes a precise question, not invented prose. Prefer one concrete sentence over a polished paragraph.

## Rewrite levels

Up to three versions per point: **conservative** (safest, fully confirmed) ·
**strong** (best version on known facts) · **punchy** (sharper — only if
still true). Pick one, say why. Every version truth-tagged;
`needs-confirmation` facts are listed as questions to the candidate, never
written into prose.

## Content actions

keep · tighten · rewrite · collapse (two bullets proving one thing → one
stronger) · split (one bullet hiding two signals → two) · move up / move
down · expand (only when missing context blocks belief) · cut (does not serve
the lane) · hold-for-evidence.

## Section repair loop — `rewrite` depth

Per section, in resume order: what must this section prove for the lane → does
it → content action per bullet → produce rewrites (levels as needed) →
confirmation questions batched at the section's end → next section. Carry
decisions forward; never re-litigate a resolved section.

## Acceptance — a rewrite ships only if

The candidate could say it aloud · every fact confirmed or tagged · voice
test passed · it serves the lane · it survives the technical reviewer, not
just the skim.
